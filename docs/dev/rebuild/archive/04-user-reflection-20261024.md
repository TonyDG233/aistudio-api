# 04 用户反思与重构方向（2026-10-24）

- 记录时间：2026-10-24
- 性质：用户口述方向，不是已批准的设计或实现计划
- 说明：以下保留原意，关键句为用户原话摘录

## 1. 对当前项目的判断

用户认为：

- 日志页、统计页、多个格式适配确实是用户提的需求，但它们被混杂在“主需求”里一起实现了，导致主线失焦。
- 项目已经失控；多个新增功能层和原有实现互相污染。
- 不想再在现有结构上继续打补丁，想重新开始。
- 唯一明确要保留的是：**先行测试和已经做过的实验不要丢掉，不要重复造轮子**。
- 新问题很多，但连功能位于哪里都不知道，无法继续让人“修”。

## 2. 对最初分流策略的反思

用户原话：

> “我感觉我从一开始的分流策略就是错的，明明是基于旧反代的实践，希望两个反代措施都在一个项目中实现，然后依照反代类型做分流，将一个账号登录一个反代途径视作一个实例或者账号登录状态，就像旧项目那样。”

当时的期望：

- 同时拥有 free 账号和 pro 账号；
- Pro 高级模型额度用完后，不必只能等 24 小时；
- 期间仍能轮询到 free 账号，保证 QQ bot 随时有模型可用。

## 3. 新的方向判断

用户原话：

> “甚至多个反代途径都不是最关键的，按反代途径来路由也很蠢。为什么不能在已经有模型标记 paid 的情况下，直接按 paid——pro 账号实例的方式路由呢？”

> “我为什么要贪一个 context 登录两个 page 呢？就是因为这个例外，我三天都在和 ai 扯皮这个最基础的概念，往返的修，WP5 和 WP7 的修复提交都不知道重复了多少次了。”

当前倾向：

- 不再把“反代途径”作为第一等路由维度；
- 模型已有 `paid` 标记时，直接路由到 Pro/paid 账号实例；
- Free 与 Pro 的调用需要隔离，保证 QQ bot 始终有可用模型，同时用户能用 paid 模型；
- 为了这种隔离，仍然需要 **多 context** 架构；
- 但不应再保留“一个 context 登录两个 page”的例外，这个例外是 WP5/WP7 反复返工的根源。

## 4. 对后续协作方式的要求

用户原话：

> “我应该拿做架构的地图，告诉 ai 我希望在哪个环节上添加哪个功能，来确保它是在树枝上长出的花，而不是凭空生出花然后胡乱嫁接在树干上。”

要求：

- 先有可理解的架构地图，再讨论功能落点；
- 每个功能必须能说清“长在哪根树枝上”，不接受凭空新增一层再强行嫁接到主干；
- 不再接受 500 行规划文档替代真实理解；
- 不再无条件信任 agent 的“已完成”；
- 方向由用户控制，agent 只做事实核对、边界确认和执行。

## 5. 保留项

- 已有先行实验、真机证据、测试、协议逆向资料不丢；
- 旧项目的账号登录状态/实例经验可作为参照；
- 多 context 架构保留，用于 paid/free 隔离；
- 需要重新确认：实例的最小定义、路由的第一维度、哪些功能属于主线、哪些是附加能力。
