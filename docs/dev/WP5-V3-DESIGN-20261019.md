## 0. 结论摘要

1. **取消默认会话 / Realm 分立**。所有浏览器上下文（Context）都是统一实例池中的平等槽位；不存在一个特权默认实例。
2. **实例池不是按组/渠道拆分的池**。组和渠道是槽位的**资格约束**，不是独立池。
3. **两类流程共用资格图，但顺序不同**：
   - 请求时路由：渠道先定，给当前请求选候选账号/槽位；
   - 实例切换/再平衡：先按紧急度选槽位，再按“最受限槽位优先 + 渠道亲和 + 轮换公平”装账号。
4. **“模型池”按“额度池（QuotaPool）”建模**：账号的模型限额/额度池是资格，不是模型清单。
5. **页面数与环境数分开计数**：全局/渠道/组数页面；Context 数单独预算。取消“一个 Realm 算一个实例”的补丁。
6. **策略组只做约束层**：账号集、`allowed_surfaces`、额度池、页面预算、权重；它不主动发起后台再平衡，也不发消息。但请求期由实例层在派发上游前完成“能力不足→切换/装载合格账号”，这一步是强制的，不是可选优化。

## 1. 参考项目结论（Ark）

Ark 的结构是：

```text
一个 Browser
└── contexts: Map<authIndex, {context, page}>
    maxContexts 控制热 context 池大小
    currentAuthIndex 只是当前激活指针
```

关键事实：

- `BrowserManager.js:41-43`：`contexts` 是账号上下文池，所有 context 平等。
- `BrowserManager.js:2078-2083`：每个账号用自身 `storageState` 创建 context。
- `BrowserManager.js:1932-2021` `rebalanceContextPool()`：按 rotation 保留 `maxContexts` 个热账号，关闭池外空闲 context，后台预载缺失账号。
- `BrowserManager.js:2311-2402` `launchOrSwitchContext()`：切号优先 fast switch 到已存在的账号 context，否则创建目标账号 context。
- `ConfigLoader.js:77`：`maxContexts` 默认 1。

**本仓要保留的**：一个浏览器、按账号 storageState 建 context、热 context 复用、fast switch、池再平衡。

**本仓要扩展的**：渠道页面角色（pg/build）、组约束、额度池资格、跨账号并发、槽位。

**本仓明确不保留的**：默认会话特权、Realm 按账号硬绑定、`max_realms` 与 `global_max_instances` 重叠。

## 2. 术语

| 术语 | 含义 |
|---|---|
| Context / Realm | 隔离 cookie jar 的浏览器上下文；本文统一叫 **Context**，“Realm”仅作旧稿别名 |
| Slot（实例槽） | 池中的一个执行位，有 `channel` 角色、当前账号、页面集合、在途数 |
| Page（页面） | chat 页或 build 页；一个 Context 可有多页 |
| Group（策略组） | 约束层：账号集、允许渠道、额度池、页面预算、权重 |
| QuotaPool（额度池） | 账号背后的模型限额池，如 free 额度、pro/argon 额度；是资格，不是模型清单 |
| Active account | 当前默认指针/新请求黏性；不拥有特殊实例 |
| Slot row | 配置中的 `(账号 × 渠道)` 预留行；是计划/优先级，不是永久 context |

## 3. 统一实例池模型

```text
InstancePool(max_contexts = N)
├── Slot 0: context + current_account + pages{chat?, build?} + in_flight
├── Slot 1: context + current_account + pages{chat?, build?} + in_flight
└── ...
```

槽位字段：

```text
slot_id
context_id
state: empty | loading | ready | busy | cooldown | retiring
channel_role: pg | build | any
current_account_id
pages: {chat: PageRef | None, build: PageRef | None}
in_flight: int
last_used: float
assigned_slot_rows: set[(account_id, channel)]
```

规则：

1. 所有槽位平等，没有默认槽。
2. 一个槽位同一时刻只绑定一个账号；在途时不可换绑。
3. 槽位空闲时可以卸载旧账号、装载目标账号；装载方式：
   - Ark 风格：关闭旧 context，用目标账号 `storageState` 新建 context；
   - 优化：在现有 context 内换 cookie、重新导航/BotGuard；语义仍是“槽位装载账号”。
4. `max_contexts` 是 Context 数上限；页面数另有预算。
5. Level A：1 个 Context 可同时有 chat/build 两页；Level B：多个 Context 跨账号并存。

## 4. 资格图（唯一事实来源）

一个账号对“某槽位/某请求”的资格由以下交集决定：

```text
eligible(account, channel, model) =
    channel.enabled
    and channel.implemented
    and group.allowed_surfaces contains channel.surface
    and account.quota_pools intersects channel.quota_pool
    and model capability allows channel.surface
    and model.account_requirement passes(account)   # pro-only / free-capable / any
    and not account.expired
    and not cooldown(account, channel, model)
```

`model.account_requirement` 是 ① 能力解析的一部分：

- `pro-only`（argon/Pro 系）→ 账号必须是 pro/paid；
- `free-capable` → free/pro 均可；
- `chat-only` → 只能 chat 面（与账号 tier 是两条独立约束）。
- 当前实现只做了 chat-only，没有做 pro-only 的账号 tier 校验；v3 必须补上。

补充：

- `group.allowed_surfaces` 与账号级 `routing.surfaces` 都只能收窄。
- `model_surfaces` 钉死只做收窄。
- 账号 tier 决定默认额度池：
  - free：`quota_pools = [free]`
  - pro/paid：`quota_pools = [pro, free]`（可配置）
- 渠道声明自己的额度池：
  - `channels.pg.quota_pool = pro`
  - `channels.build.quota_pool = free`
- 若两个渠道实际共用同一额度池，把 `quota_pool` 配成同名即可。
- 运行时 429/限额状态由 rotator 记录；静态额度池资格与运行时冷却分开。

示例：

```yaml
groups:
  - name: free
    match_tier: [free]
    allowed_surfaces: [build]
    allowed_quota_pools: [free]
  - name: pro
    match_tier: [pro, ultra, plus]
    allowed_surfaces: [chat, build]   # pro 可两个渠道都开
    allowed_quota_pools: [pro, free]

channels:
  pg:    { enabled: true, quota_pool: pro,  max_pages: 1 }
  build: { enabled: true, quota_pool: free, max_pages: 1 }
```

## 5. 两类流程

### 5.1 请求时路由

```text
① 渠道/能力解析（前缀或裸名）
② 候选账号 = eligible(account, channel, model)
③ 组约束（已在资格图）
④ 排序：黏性 → 冷却健康 → 渠道亲和 → 权重/请求量 → last_used → account_id
⑤ 槽位落地（派发上游之前，强制完成）：
   当前槽位账号合格且空闲/未满载 → 复用
   当前槽位账号不合格（能力/额度池/tier/渠道不匹配）但槽位空闲 → 切到合格账号
   当前槽位在途或不可切 → 找其它空闲槽位装载合格账号
   否则未达 max_contexts → 新建槽位
   否则挂起请求等待（≤5s 发 : resolving-instance），或按原因显式报错
⑥ 实际向上游发送请求
⑦ 首字节前失败链：同账号重试 / 换槽位 / 熔断
```

关键点：

- **请求不会先发给不支持的实例再报错**。若当前实例账号不具备 pro 能力、但候选列表里有 pro 账号，请求必须先在池内切换/装载 pro 账号，再向上游派发。
- **请求会保留**：切换/装载期间请求处于 pending，不丢弃、不降级、不改模型；等待有界，超时/无候选时显式报错。
- **不能为切换打断在途流**：当前槽位在途时，改用其它空闲槽位或新建；没有可用槽位时等待/报错。
- 请求期只处理“已有或可创建的槽位”，不做全局后台再平衡；后台再平衡由 §5.2 独立触发。

### 5.2 实例切换 / 再平衡

触发源：

- 手动切号；
- `auto_switch`；
- 冷却/过期/账号删除；
- 槽位失效（页面崩溃/context 关闭）；
- 空闲回收/预热；
- 策略组或渠道配置变更。

流程：

1. 列出需要处理的槽位，按紧急度排序：
   - 失效/冷却/过期；
   - 空槽补位；
   - 策略变更需重分配；
   - 空闲最久（回收/预热）。
2. 对每个待切换槽位，计算 eligible 账号集合。
3. **最受限槽位优先**：合格账号数最少的槽位先分配。
4. 对每个槽位按分数选账号：

```text
score = (
  channel_affinity,      # 原生渠道优先：free→build、pro→pg；pro→build 是跨面回退
  stickiness,            # 当前健康账号优先保留，减少抖动
  occupancy_penalty,     # 已占其它槽位越多越靠后
  group_weight_bias,     # requests / weight，越低越优先
  last_used,
  account_id,            # 确定性兜底
)
```

5. 分配一个账号后，从其它槽位候选中移除该账号，避免一个账号占满多个槽位。
6. 在途槽位绝不换绑；只处理空闲/失败槽位。

示例：2 个槽位（pg、build），账号 pro1、pro2、free1…free48。

- `pg` 合格：pro1、pro2；`build` 合格：free1…48 + pro1、pro2。
- 最受限的是 `pg` → 先给 pro1；
- `build` → 原生优先 free1；
- 结果：pro1@pg + free1@build；build 不被 pro 浪费，pg 也不会因 pro 被 build 占用而空缺。
- 若无 free，`build` 才回退 pro2；若 pro1 冷却，`pg` 换 pro2。

## 6. 渠道、实例角色与额度池

- 渠道在请求 ① 固定，链内不换面。
- 槽位有 `channel_role`，但池不按渠道拆；角色只用于资格/排序/预算。
- 同一账号可占多个 slot row（如 pro@pg + pro@build）。
- 一个 Context 在 Level A 可同时承载 chat/build 两页；Level B 每个账号可有独立 Context。
- 渠道额度池用于避免“build 被 pro 占用却跑不出免费额度”或“free 进 pg 浪费请求”。
- 渠道 `max_pages` 是该渠道页面上限，不是预留；全局/组预算仍取最严。

## 7. 预算口径

| 预算 | 计数单位 | 说明 |
|---|---|---|
| `global_max_pages` | Page | 所有 chat/build 页面总数 |
| `channels.<ch>.max_pages` | Page | 该渠道页面数上限 |
| `groups[].max_pages` | Page | 该组账号拥有的页面数上限 |
| `max_contexts` | Context | 浏览器上下文数上限（含首个） |
| `planned_instances` | Slot row | 启用槽位行数 |

默认值建议（需用户确认）：

```yaml
routing:
  global_max_pages: 2
  max_contexts: 2

channels:
  pg:    { enabled: true,  max_pages: 1, quota_pool: pro }
  build: { enabled: false, max_pages: 1, quota_pool: free }
  official: { enabled: false, max_pages: 0, quota_pool: official }

groups:
  - max_pages: 2
```

理由：

- 黄金模板 `pro@pg + free@build` 是 1+1=2；
- 默认 `pg=1/build=1` 强制两个渠道各留一个位置，避免一个渠道吃满全局 2；
- 需要单渠道开 2 页时显式调高该渠道 `max_pages`，并接受另一个渠道被挤占；
- Context 数与 Page 数分开，不再出现“3 页 vs 2 上限”的假象；
- 取消 `max_realms`，统一为 `max_contexts`。

## 8. 槽位表

- `slots: [{account_id, channel, enabled, note}]`。
- 槽位行是**预留/优先级**，不是永久 Context。
- 计划数 = 启用槽位行数；当前数 = 活页面数。
- 槽位行不绕过预算；超出 `global/channel/group/context` 的行只能排队或保持未激活。
- 50 个账号可以有 50 行，但同时只有预算允许的槽位/页面存活。

## 9. Borrow

- 默认关。
- 主槽不可用（冷却/未就绪/切换中），且另一账号的空闲槽位渠道与额度池兼容时，首字节前临时借入。
- 不改变 `active_account`，不触发账号切换。
- 消耗借入槽账号的额度，计入预算。
- 日志：`[instance:borrow] from=slotN account=... reason=...`。

## 10. 失败链

- 同账号重试走 `MAX_RETRIES`，不消耗切换预算。
- 换槽位/换账号走 `max_switches=2`。
- 滚动 10 分钟 ≥5 次失败切换 → 熔断 5 分钟。
- 首字节后不切换；错误显式返回 `surface_*`。
- 错误码沿用：`surface_no_capable_account` 403、`surface_quota_exceeded` 429、`surface_switch_exhausted` 503 等。

## 12. API 与可观测性

### 12.1 模型列表规则（防重复）

- 单模式：只返回裸模型 ID，不返回前缀。
- 多模式：只返回**启用且已实现**渠道的规范前缀（`pg/`、`build/`）；`chat/`、`playground/` 仅作为输入别名，**不在列表中出现**；`official/` 在未实现前**不出现**。
- 每个模型最多按“真实渠道数”出现，不按别名数出现；同一模型在两个渠道都可用时，可返回两条规范前缀 ID，或在同一模型条目上附 `channels: ["pg","build"]` 元数据，由 UI 决定展示方式。
- 模型在某渠道不可用时，不生成该渠道的前缀条目；不得为了“列表完整”伪造未支持组合。
- 当前 `/v1beta/models` 与 `/v1/models` 只返回裸模型 ID，没有前缀重复问题；多模式前缀列表属于后续设计，必须遵守上述规则。

### 12.2 实例与路由快照

- `GET /surface/instances`：返回 contexts、slots、pages、current/planned、budgets、quota pool 资格摘要；不返回 cookie/密钥。
- `GET /routing/state`：熔断、切换预算快照、最近切换事件计数。
- 日志前缀：
  - `[instance:assign] slot=... account=... channel=... reason=...`
  - `[instance:switch] slot=... from=... to=... reason=...`
  - `[instance:reclaim] slot=... account=...`
  - `[instance:borrow] ...`
  - `[quota:deny] account=... channel=... pool=...`
- 策略组本身不发消息、不主动触发切换；它只提供资格/预算/权重。请求等待期仍只发 SSE 注释 `: resolving-instance`。

## 13. 从 v2 迁移

需要删除/替换：

1. 删除“默认会话 vs Realm”的二元结构；`BrowserSession` 变成槽位 0 的实现细节，不是特权实例。
2. 删除 `RealmPool` 的 `_by_account` 硬绑定；改为按槽位装载账号，账号→最近槽位仅作软亲和。
3. 删除 `max_realms` 与 `global_max_instances` 的重叠；改为 `max_contexts` + `global_max_pages`。
4. 撤销“一个 Realm 算一个全局实例”的计数补丁；页面数与环境数分开。
5. `auto_switch` 从“切全局默认账号”改为“按槽位角色和目标选择账号”；不触碰在役槽位。
6. 保留并复用：渠道注册表、组 `allowed_surfaces`、账号 `AccountMeta.routing`、失败链/切换预算/熔断、borrow、槽位计划数。
7. `slots` 从排序提示升级为槽位分配输入；但仍不是永久 context。

## 14. 测试与验收

### 单测

- 50 个账号、2 个槽位、顺序轮换：context 数始终 ≤2，页面数 ≤ global。
- free 组只能装载 build 槽；pro 可装 pg/build；free 不进入 pg 候选。
- 额度池不匹配 → 资格失败，不是低优先级。
- pg 最受限时先分配，build 优先 free，pro 回退。
- 在途槽位不换绑；空闲槽 LRU 回收/预热。
- 预算：global/channel/group 页面数，`max_contexts` 环境数，四者取最严。
- borrow：首字节前借入兼容槽；不改变 active account。
- 失败链：重试不消耗切换预算，换槽位计 2 次，熔断 503。
- 账号 routing 只收窄；刷新/保活后不丢。

### 真机

- 2 个槽位轮换 3 个账号：context 数不增长，请求成功。
- pro chat + free build 同时在线；两个流互不打断。
- build 槽优先 free，pro 不抢 build；pg 不会因 pro 被 build 占用而空缺。
- 渠道预算 1/1 + global 2：第三个页面请求显式 429。
- 空闲回收后重新装载账号成功。
- argon 仅做必要验证（≤2 次）。

## 15. 开放决策

1. 渠道默认 `max_pages`：建议 1/1；若产品希望单渠道可吃满全局 2，则改为 2/2 并在 UI 明确“上限非预留”。
2. 额度池来源：先配置（tier→pool + channel.quota_pool），后续可接探测。
3. pro→build 是否默认允许：建议允许但作为回退；原生 free→build 优先。
4. `max_contexts` 默认 2 是否足够：黄金模板是 2；内存紧张可调 1，退化为单 context。
5. 后台切换是否推 SSE/WebSocket 事件：首期只做日志 + 只读快照，UI WP7 再定。
