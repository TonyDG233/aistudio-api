## 0. 为什么要做 v4

V3 把内部实现概念直接产品化了：

- Context 被当成实例；
- Slot、Slot row、Page 被并列展示；
- `planned_instances`（Slot row 数）和活页面数被放在同一个 `current/planned` 里；
- 资格、命中、预热进入账号页。

结果是用户看到：

```text
实例 / 槽位 / 页面 / 资格 / 命中 / 计划实例
```

但用户真正需要的心智模型只有：

```text
同时登录了几个账号
每个账号能否接请求
最近启动的是哪个实例
如何新建、关闭、换账号
```

v4 的目标是：**把实例收敛为用户侧唯一抽象，把 Context/Page/Slot 全部降为内部资源。**

---

## 1. 用户侧唯一抽象：实例

```text
实例 = 一个同时登录的账号会话
```

它近似于 V3 的 Context，但**不等于**内部 Context 对象，也不包含 Page/Slot 子概念。

- 一个实例对应一个账号；
- 实例有稳定编号 `#1`、`#2`；
- 实例占用一个并发登录容量；
- `max_contexts` 就是实例上限，也是反代能同时路由到的账号数；
- 同一账号同时服务 PG 和 Build 时，仍然是**一个实例**；两个渠道是实例内部能力，不是两个实例。

```text
实例 #1 · 账号 A · 服务渠道：PG + Build · 使用中
实例 #2 · 账号 B · 服务渠道：PG         · 使用中
```

### 1.1 不存在的概念

以下概念不进入用户 API/UI：

- Slot
- Slot row
- Page
- planned_instances
- 资格
- 命中
- 预热
- 页面数 / 页面上限
- 当前/计划

它们只能存在于 infrastructure 或高级诊断，不作为业务字段。

## 2. 领域模型

```text
Instance（聚合根）
├── id                 # 稳定 ID
├── number             # 用户可见编号
├── account_id
├── state              # starting | active | reclaiming | invalid
├── channels           # 当前可服务的渠道集合（pg/build）
├── in_flight          # 在途请求数
├── latest             # 是否为最近启动的实例（仅展示）
├── created_at
└── runtime_ref        # 内部资源引用，不对外暴露
        │
        ├── Context     # 浏览器隔离环境；一个实例一个 Context
        └── Page        # PG/Build 页面；同账号多渠道时可有多个
```

### 2.1 状态

```text
starting    冷启动中，暂不可接请求
active      已登录，可接请求
reclaiming  已关闭，Context/Page 缓存回收中
invalid     账号失效/登录态失效，需关闭或重新登录
```

没有 `stopped` 实例。

- 关闭实例后，实例从列表移除，容量释放；
- 缓存尚未释放的短暂窗口显示 `reclaiming`；
- 没有账号占用时，不存在实例，只剩容量数字 `实例 2 / 2`。

### 2.2 最新实例

`latest` 只表示“最近启动的实例”，是展示字段，不参与路由：

- 新实例启动成功后成为 `latest`；
- 关闭 `latest` 后，回退到最近启动的剩余实例，或为空；
- 不提供“切换指针”或“设为优先”；
- 不影响资格、权重、排序、在途请求；
- UI 可用 `最新实例 ?` 表达，`?` 用来说明这是参考项目 fast switch/current context 的界面致谢。

如果未来需要真正的“优先实例”，必须新增后端路由字段并单独设计；不能复用 `latest`。

## 3. 资源分配

### 3.1 常见情况：2 个账号

```text
账号 A → 实例 #1 → Context A → Page(PG)
账号 B → 实例 #2 → Context B → Page(Build)
```

资源：

```text
2 个实例
2 个 Context
2 个 Page
```

不同账号不能共享 Context，因为 cookie jar 不同。

### 3.2 同一账号两个渠道

```text
账号 A → 实例 #1 → Context A
                     ├── Page(PG)
                     └── Page(Build)
```

资源：

```text
1 个实例
1 个 Context
2 个 Page
```

这是后端兼容优化，不产生第二个实例，也不进入用户 UI。

### 3.3 分配规则

```text
for each active instance:
    ensure exactly one Context for its account
    for each channel served by the instance:
        ensure one Page
```

- 同账号多渠道共享 Context；
- 跨账号绝不共享 Context；
- Page 只在渠道实际使用时创建；
- 默认不预加载；
- 内存充足时的预加载/额外页面属于高级设置，默认关闭。

## 4. 容量与内存

### 4.1 用户可见容量

```text
max_contexts = 最大同时登录实例数
```

UI 只显示：

```text
实例 2 / 2
```

新建实例超过上限时明确返回 `instance_capacity_exhausted` 409，不静默淘汰其他实例。

### 4.2 内部资源预算

以下仍由后端管理，不进入用户 API/UI：

- 全局页面硬顶
- 单渠道页面上限
- 组页面上限
- 单实例内存估算

默认策略：

- 每个 active 实例一个 Context；
- 每个服务的渠道一个 Page；
- 不做预热；
- 页面预算只作为内存保护，不参与用户操作。

高级设置可开放：

- 预加载同账号第二渠道页面；
- 提高页面上限；
- 快速切换缓存。

默认全部关闭。

## 5. 路由与实例操作

### 5.1 自动路由

请求仍按 V3 的资格图与排序：

```text
渠道/能力 → 候选实例 → 组约束 → 排序 → 页面落地
```

候选实例 = 所有 active 实例。

排序继续使用：

- 健康/冷却
- 渠道亲和
- 组权重
- 最久未使用
- 请求数/权重
- 编号兜底

`latest` 不参与排序。

### 5.2 启动、关闭与换账号

用户手动操作只有：

- 新建/启动实例；
- 关闭实例；
- 换账号（`reassign`）。

没有“切换当前实例”或“设为优先实例”：

- 新实例启动后自然成为 `latest`；
- 路由仍自动选择所有 active 实例；
- 若要限制某个账号，使用 P3 的自定义策略组；
- 若要释放容量给另一个账号，关闭旧实例或 `reassign`。

`reassign` 保留实例编号，其他实例不受影响。

## 6. 对外 API

新增用户 API，旧 `/surface/instances` 保留为诊断快照。

```text
GET    /api/instances
POST   /api/instances                 { account_id }
DELETE /api/instances/{id}
POST   /api/instances/{id}/reassign   { account_id }
```

### 6.1 列表

```json
{
  "max_instances": 2,
  "latest_instance_id": "inst_1",
  "instances": [
    {
      "id": "inst_1",
      "number": 1,
      "account_id": "acc_a",
      "state": "active",
      "channels": ["pg", "build"],
      "in_flight": 1,
      "latest": true
    }
  ]
}
```

不返回：

- Context ID
- Page ID
- Slot/Slot row
- 资格/命中/预热
- planned 页面计数

### 6.2 新建

- 占用一个 `max_contexts` 容量；
- 账号必须存在且未失效；
- 同一账号已有实例时返回 409 `instance_already_exists`；
- 超限返回 409 `instance_capacity_exhausted`；
- 冷启动异步完成，返回 `starting`。

### 6.3 关闭

- 有在途请求返回 409 `instance_busy`；
- 否则进入 `reclaiming`，释放 Context/Page 后从列表移除；
- 不关闭其他实例。

### 6.4 最新实例

- `latest` 由启动顺序自动维护；
- 没有设置接口；
- 不参与路由。

### 6.5 换账号

- 目标实例必须无在途；
- 原 Context/Page 回收；
- 新账号在同一容量位冷启动；
- 实例编号保持不变；
- 其他实例不变。

## 7. 配置与迁移

### 7.1 废弃

以下配置不再作为用户概念：

- `features.slots`
- `planned_instances`
- `routing.prewarm`（未实现）
- 用户可见的页面预算

兼容策略：

- 旧 YAML 可读取，不报错；
- 新代码不再写 `slots`；
- 迁移时忽略 slot rows，不把它们当实例；
- UI 不展示任何 slot 字段。

### 7.2 保留

- `max_contexts`：实例上限
- `global_max_pages` / 渠道 / 组页面预算：内部资源保护
- 组、渠道、额度池资格：路由内部使用
- borrow、熔断、切换预算：内部策略
