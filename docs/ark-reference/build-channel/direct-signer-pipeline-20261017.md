# MakerSuite 直连签名器方案（设计草案）

> 状态：草案（仅文档，不含代码）。
> 实现起点：从 `main` 新开的分支 `feat/makersuite-direct-signer`。
> 2026-10-17。分支 `fix/makersuite-generatecontent-bridge` 自本日起**封存**（仅作档案与证据来源，不再修改）。

## 1. 问题

平台曾提供"App 无凭据请求 → 预览宿主翻译/签名 → 内部代理 RPC"的通道（占位符 `GEMINI_API_KEY` 被换为真实凭据）。该通道的生成 POST 曾被 Google 整体拒绝（裸 400 INVALID_ARGUMENT，约 0.6s），2026-10-17 已恢复（原生路径多次 200 实测）。

需求：提供一条**不依赖该通道存续**的直连式生成链路（自带凭据语义、自持传输、真流式），作为健康期的可选路径与断供期的回退。

## 2. 三条原理（本项目得出的结论，防重复踩坑）

1. **谁拥有 socket，谁才能流式。** SSE/分块只是"响应 body 按到达节奏可读"；Playwright 的 `route.fulfill` 没有写入通道 ⇒ 拦截式回填天然一次性（封存分支的桥因此必然非流式，这是构造性结论而非调参问题）。
2. **`route.continue` 不可用于改写该 RPC 的 URL**：不允许改协议（https→http）；跨源改写会破坏预检与主请求的配对（CORS 记账）⇒ 被浏览器直接拦。两者均已实测。
3. **浏览器页内无法自造 WAA 客户端实例**（Angular `NG0203`：`inject()` 必须在注入上下文内；`M.n(M.TB)`、`new M.TB()`、root 类扫描全部失败）⇒ 签名所需的 `tb` 只能经"宿主构造请求时调用 `Cn`"来捕获；引导办法见 §4。

## 3. 方案

三个角色，职责与所在地：

| 角色   | 做什么                                                                                                                                                                        | 在哪                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 签名器 | `acquire()` 获得 `tb`；`execute(request)` 用页面凭证（`authorization` / `x-goog-api-key` / `x-goog-authuser`）+ `Cn` token 调 `MakerSuiteService/GenerateContent`，逐元素读流 | 主页面 realm（与旧桥相同的注入方式：`addInitScript` + `page.evaluate`） |
| 通道   | 页面**自持**一条到 Node 的连接；采用产线已有形态 `ws://127.0.0.1:9998`（build.js 每日在用）。**不使用回环 HTTP 端点**                                                         | 页面 ↔ 服务端                                                           |
| 端点   | `GenerateContent`（产品 UI 同款方法，稳定性最高）                                                                                                                             | Google 内部 RPC                                                         |

- **服务端（Node 进程）**：请求分发、凭证/收割材料供给、SSE 输出。不拦截任何网络请求。
- **页面（浏览器内）**：签名与上游调用、逐帧转发。
- **Playwright**：仅浏览器宿主与脚本注入；**不做任何 route 拦截/改写**。

## 4. 未验证点（决定方案是否成立，先说丑话）

1. **主页面 realm 自持 WS 到 Node**：iframe 侧已被产线证明（build.js 的 WS）；主页面未单独测。零成本可测。
2. **`Cn` 捕获引导**：需要"任一宿主请求经过"才会调 `Cn`。设计 **warm-up**：发一个 `models/__warmup__:streamGenerateContent` 请求让宿主完成签名流程，本地拦截并本地应答，**不触达上游（0 额度）**。未实测。
3. **失败语义**：token 空 / 401 / 端点拒绝三类下的行为与退避策略。需 1 次真机调用做端到端验证（判据：SSE 事件时间戳分散）。

## 5. 复用件（来自封存分支，迁移时带走）

- codec 的"GenerateContent 元素 → Gemini 块"半套（`convChunk` / `scanArrayElements`）；
- 凭证捕获（`Cn` 包装，含"优先带 key 实例"的修正）与旧 RPC 请求头收割（白名单回放）；
- 逐帧读取循环（`runStreamResponse` 的读循环）；
- WS 消息形态（现有 build.js 协议，服务端解析逻辑不变）。

**丢弃**：route 拦截、旧信封编解码、`route.fulfill` 回填、回环端点（`LocalStreamServer`）、以及"默认开启"的一切开关。

**默认策略**：新链路全部默认关闭；原生路径保持默认；显式开启才生效。

## 7. 注意力事项

- 本方案与 ATG 正交。ATG 对交付形态的影响当前存在**未解样本矛盾**（2026-10-17 样本：原生+prefer=单块 ×3；原生+off=渐进 ×1；与用户侧酒馆经验相反），本方案不做定论，也不使用 ATG 的解释。
- 若 `GenerateContent` 也被关闭：浏览器侧无直连替代，只剩"官方 App 服务端 + 平台注入 key"模型（代价：额度绑 GCP 项目、失去多账号池）——仅作备案，不在本方案内。
